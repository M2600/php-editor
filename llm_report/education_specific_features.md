# php-editor に見る「教育用途・情報システム開発実習特化」機能・UI カタログ

作成: 2026-07-06
対象: 通常の開発環境（VSCode等のIDE、Postman、GitHub等）と比較して異質・過剰に見えるが、
「大学の授業で多人数の学生に情報システム開発を実習させる」という文脈だからこそ実装されている機能・UIを抽出したもの。

関連ドキュメント: `llm_report/conference_report.md`（開発史・時系列changelog）。本レポートはその中の「授業利用で得られた知見」を機能・UI単位で横断的に再整理したもの。

---

## 0. 視点

一般的な開発環境は「開発者自身が信頼できる前提」で作られている。php-editorは以下の点でこの前提が成立しない:

- 利用者（学生）は初学者であり、git・API開発ツール・シェルの知識を持たない
- 利用者は数十人単位で同時に同一サーバー上でコードを書き、**実行**する（＝任意コード実行環境を多人数に提供している）
- 教員という「学生を管理・監督する」別ロールが存在し、クラス単位の運用が必要
- 「授業中に不具合が起きても即座に対応できない」「学期をまたいで運用を引き継ぐ」という教育カレンダー特有の制約がある

この結果、通常の個人用コードエディタには存在しない機能・UIが多数実装されている。

---

## 1. 学生を「敵対的ユーザーになりうる」前提で設計された実行サンドボックス

一般のローカルエディタは「実行＝自分のマシンで自分のコードを動かす」だけだが、php-editorは「他人（学生）の書いた任意のPHPコードをサーバー上で実行し、その結果を安全に返す」という、通常のエディタにはないサーバー運用上の責務を負っている。

- **php-cgi + `open_basedir` による実行時サンドボックス**（`docs/PATH_SANITIZATION.md`, `docs/SECURITY.md`）: ユーザーが書いたPHPを`php-cgi -d open_basedir=/path/to/user/root/`で強制的にユーザールート配下にのみアクセス可能な状態で実行。`fopen()`や`include`での越境读み取りもエンジンレベルで遮断する。個人用エディタなら不要な発想。
- **サーバー内部パスの出力からの除去**（`sanitizeOutputPaths()`, `docs/PATH_SANITIZATION.md`）: 構文エラー・実行時エラー・例外メッセージに含まれる`/home/user/data/php_editor/sandbox/user123/...`のようなサーバー内部パスを、学生に見せる出力からは全て除去し相対パスに変換。一方で管理者向けログには意図的にフルパスを残す。「学生に見せてよい情報」と「運用者に必要な情報」を明確に分離する設計判断。
- **エディタ用/ユーザープログラム用のセッション名分離**（`PHP_EDITOR_SID` / `USER_PROGRAM_SID`、`docs/SESSION_SECURITY.md`）: 学生が`error_log()`で`$_COOKIE`を出力したり`session_name()`を偽装したりしてエディタ側のセッションを乗っ取ろうとする攻撃シナリオを明示的に想定した対策。「学生の書いたコードが同じサーバー上で動く」という構成でなければ発生しない脅威モデル。
- **非公開ファイルの視覚的マーキング**（`js/modules/core/config.js:107-120` `PRIVATE_FILE_PATTERNS`、`js/modules/core/file-manager.js:15-41` `markPrivateFiles()`、`MEditor/MEditor.css:585-594`）: ドットファイルや`config/`ディレクトリ配下のファイルを、実行時にアクセスできないことが一目でわかるよう緑色のテキスト＋ツールチップで表示する。設定ファイルや認証情報を「見せているが実行はできない」ことを初学者に理解させるためのUI上の工夫であり、単なる`.gitignore`的な非表示化ではなく「あえて見せて教える」設計になっている。

## 2. クラス・ロール管理 UI（教員／学生／管理者の三層構造）

一般の開発環境にはユーザーロールという概念自体が薄いが、php-editorは「クラス」を単位とした運用のためのUIと状態遷移を持つ。

- **学内認証基盤(BitArrow)とのOAuth連携ログイン**（`api/includes/ba_auth.php`, `api/ba_login.php`）: 大学の既存アカウントで直接ログインでき、パスワード管理を学内システムに委譲。ba loginの有効/無効自体を`BAAuth::isEnabled()`（`config.php`の`bitarrow_login_enabled`）で切り替え可能にしており、ログイン画面（`templates/login.html:112,177,263`）のボタン表示・非表示を運用フェーズに応じて出し分けられる。
- **「教員が一度もログインしていないクラスは学生が使えない」というクラス有効化フロー**（`api/ba_login.php:53-71`）: 教員ログイン時に`class`未選択なら`class_not_selected`、学生ログイン時に対象クラスが未有効化なら`class_not_activated`を返し、「担当教員にBitArrowへのログインを依頼してください」という案内を表示する。これは学期開始時の実際の運用フロー（教員がまずクラスを開設してから学生が使い始める）をそのままシステムの状態遷移として実装したもので、一般的なSaaSの「管理者が先にサインアップする」設計に近いが、教員による意図しない放置を学生側のエラーメッセージとして能動的に検知・案内している点が教育現場特有。
- **1クラス複数教員対応の`.owner`ファイル方式**（`api/file_functions.php:95-140`）: クラスのオーナー情報をDBではなく`.owner`ファイルへの1行1教員IDのリストとして管理し、別の教員のログインは冪等な追記登録（`addClassOwner()`）として扱う。データベースを持たずファイルシステムだけで多対多の権限関係を表現する、この種の小規模教育システムらしい実装。
- **教員初回アクティベート時の案内バナー**（`api/ba_login.php:84-87`, `templates/teacher.html:10-13,26-33`）: クラスを初めて有効化した教員だけを`teacher.php?activated=1`にリダイレクトし、使い方・注意点（「学生のファイルは即座に公開される」等）を表示。既存クラスへの再ログインでは表示しない、という一度きりのオンボーディングUI。
- **管理者専用の代理ログイン（なりすまし）機能**（`api/proxy_login.php`、`templates/admin.html:17-33,56-206`）: ユーザー一覧から任意の学生に代理ログインし、学生からの「動かない」という質問に対して実際の画面を再現してサポートできる。ただし編集は`readonly`フラグで強制的に禁止され、`js/main.js:97-150,368-370`でエディタを`setReadOnly(true)`にし警告バーを常時表示する。「サポートのために覗く」権限と「勝手に書き換えない」制約をセットで実装しており、これも一般の開発環境には存在しない発想（本人以外が本人のセッションで動くことを前提としたUI）。
  - 監査ログ（`logProxyLogin()`）も実装済みで、誰がいつ誰になりすましたかを記録する。
  - なお「教員ロールは編集不可・実行のみ可」という制約は`memo.md`に構想として書かれているが、role=teacherに直結した強制ロジックは現状コード上には見当たらず、実装は代理ログイン（admin限定）にとどまる。構想と実装のギャップとして発表時に言及可能。

## 3. 「Postman・スマホ実機・DBを使わない」情報システム実習向けの実行UI

情報システム開発の授業（Web API、レスポンシブ、フォーム処理など）を、外部ツールを一切インストールさせずブラウザだけで完結させるための機能群。

- **API開発モード / Webページモードの切り替え**（`js/modules/core/config.js:130` `RUN_MODE`、`js/main.js:998,1009-1053,620-650`）: 「実行結果をiframeでWebページとしてプレビューする」通常モードと、「GET/POST/JSONペイロードを指定してレスポンスをコンソールに出力する」API開発モードをUI上のタブで切り替えられる。JSON直接入力エディタ（`postJsonEditor`）も備え、学生はPostmanやcurlを別途学ばなくてもAPIエンドポイントの動作確認ができる。「授業内で一つのツールに全実習フローを閉じ込める」という教育現場の制約から生まれた機能。
- **QRコードによるスマホ実機アクセス**（`js/qrcode.js`、`js/modules/editor/ace-editor.js:282-324`、上部メニュー「⊞QR」ボタン `js/main.js:571-596`）: 現在編集中ファイルの実行URL（GETパラメータ込み）をQRコード化してポップアップ表示する。レスポンシブデザインやスマホ向けフォーム実装の実習で、学生が自分のスマホで即座に動作確認できるようにする機能で、PC単体開発が前提の一般的なIDEには存在しない。
- **データベースを使わないファイルシステムベースの永続化を前提にした設計全体**（`memo.md`のクラス機能設計メモにも明記）: ユーザー管理・クラス管理・バージョン管理のいずれもRDBを立てず、ディレクトリ構造と隠しファイル（`.owner`等）で表現している。これは「学生の授業環境にDBサーバーの運用・障害対応まで持ち込みたくない」という、単一目的の教育システムならではの技術選定。

## 4. git未経験者向けに「git用語を一切見せない」バージョン管理UI

一般の開発環境（VSCode + Git等）はgitの概念（コミット、ブランチ、revert等）をそのままUIに露出するが、php-editorはgitをバックエンドの実装手段としてのみ使い、UI上は完全に別の語彙で提示する。

- **タイムスタンプ付きスナップショット一覧**（`js/modules/core/history-panel.js`、全396行）: 内部的には`c.hash`/`c.message`としてコミット情報を保持しているが、UIには「現在のバージョン」バッジ（262-289行）、「復元」ボタン（302-310行、最新版では非活性化）、展開式の「差分」ビュー（299-356行、追加/削除行を色分けしてAceエディタで表示）としてのみ表示され、branch・commit・revertといった単語は画面上に一切出てこない。
- **「復元」を破壊的操作にしない設計**（`api/git_manager.php`）: `git reset --hard`は使わず、`git checkout {hash} -- .` → `add -A` → `commit`という「復元も新しいコミットとして記録する」方式を採用。タイムラインが常に一方向に進むため、「復元の取り消し」も同じ「復元」ボタンで実現できる。git未経験者に矢印付きの分岐図を理解させることなく「巻き戻し」を提供する工夫。
- **3種類の自動スナップショット契機**: ①AIエージェントのターン完了後、②手動保存（Ctrl+S）成功後、③復元操作自体、の3つのタイミングで自動的にコミットが作られ、学生は「保存する」以外の操作を意識する必要がない。
- **読み取り専用モード（代理ログイン中等）でのスナップショット/復元拒否**（`api/git_manager.php:19-22,46-50`）: 上記2章の代理ログイン機能と連動し、なりすまし中に誤って学生の履歴を書き換えないようガードされている。

## 5. AIコーディングエージェントに対する「無断で書き換えさせない」ガードレールUI

一般的なAIコーディングツール（Cursor, Copilot等）もdiff確認UIを持つが、php-editorでは「初学者が何が起きたか理解しないままAIに丸投げする」ことを防ぐための、より強制力の強いUIフローになっている。

- **編集前の必須確認ダイアログ＋ファイルロック**（`js/modules/ai/ai_tools/fileEditor.js:262-388,390-508`、`APP_STATE.IS_SHOWING_EDIT_CONFIRMATION` フラグ `config.js:132`）: AIがファイルを編集・新規作成しようとするたびに`diffApplyMenu()`による承認/拒否ダイアログを表示し、承認待ちの間は`openFile()`（`js/modules/editor/ace-editor.js:76-83`）が他のファイルを開く操作自体をブロックしコンソールに警告を出す。「AIが勝手に複数ファイルを次々編集し、学生が気づかないうちに授業の課題ファイルが書き換わる」ことを防ぐ、教育現場ならではの強い制約。
- **ファイル削除に対する確認ダイアログ**（`fileEditor.js:1659`）も同様に必須。
- **小型・無料のローカルLLM（qwen等）でも編集ツールが実用的に動くための信頼性改善**（`llm_report/conference_report.md` 3.3節に詳細、2026-06-12対応）: 商用の高性能クラウドLLMではなく、教育機関が予算をかけずに使えるローカルLLMを前提にせざるを得ない事情から、`readFile`の出力切り捨てや二重JSONエンコードといった、性能の低いモデルほど失敗しやすい癖を丁寧に潰し込む改修が行われている。これは「単一の賢いモデルを前提にした設計では教育現場では通用しない」という、営利目的の開発環境にはあまり出てこない制約から生まれた作業。
- **AI編集範囲の限定は名目上の実装にとどまる点**（`fileEditor.js:21-40` `resolveFilePath()`）: 「AIが編集できる範囲をユーザーが開いているディレクトリ内に制限する」という設計意図はドキュメント・changelog上に明記されているが、実装は相対パス解決止まりで、絶対パス指定時の強制境界にはなっていない。実際の安全性は1章のパスサニタイズ層（`isPathInUserRoot()`等）に依存しており、UIレベルのガードと実際のセキュリティ境界が別レイヤーにある点は発表時に正確に説明すべきポイント。

## 6. その他の小さいが象徴的なUI

- **画像プレビュー機能**（`js/modules/editor/ace-editor.js:210-221`）: base64画像をそのままビューア表示。学生がアップロードした演習用画像素材の確認に使う、一般のコードエディタにはあまりないビューア機能。
- **アップロードダイアログの誤操作防止**（`js/modules/ui/dialogs.js:869-1007`）: ファイル未選択時はアップロードボタンを非活性化。`memo.md`には「アップロードが目立ちすぎる」という授業内フィードバックが記録されているが、それに対応する特別なUI制御（ボタンの視覚的な抑制など）は現状のコードには見当たらず、未対応の課題として残っている。

## 7. まとめ：3つの軸

本調査で見つかった「教育・情報システム開発実習特化」の機能・UIは、次の3つの軸に整理できる。

| 軸 | 一般の開発環境との違い | 代表例 |
|---|---|---|
| **多人数・敵対的利用者の前提** | 「開発者=信頼できる本人」ではなく「学生=任意コードを実行する多数の他者」として扱う | php-cgi sandbox、パス漏洩防止、セッション名分離、非公開ファイルの可視化 |
| **教育現場特有の組織構造** | 個人アカウントではなく「クラス」「教員」「学生」という多層的な権限・ライフサイクルを持つ | BitArrow連携・クラス有効化フロー、`.owner`複数教員対応、代理ログイン＋readonly強制 |
| **初学者の認知負荷を最小化するUIの翻訳** | 専門用語（git, API, ネットワーク）をそのまま見せず、実習に必要な操作だけに抽象化する | git用語を隠した「復元」UI、Postman代替のAPI開発モード、QRコードでの実機確認、AI編集の強制確認フロー |

これらはいずれも、単体の技術としては目新しくないが、「学期という区切りの中で、多数の初学者に、サーバー上で実際にコードを動かす経験をさせる」という要件の組み合わせによって、通常の商用開発環境やIDEには現れない形に仕上がっている点が特徴である。
